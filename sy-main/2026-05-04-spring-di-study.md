# 2026-05-05 Spring DI 학습 정리

## 개발 편의 기능과 기본 개념

- `Option + Enter`: 없는 클래스(예: `Payment`)로 빨간 줄이 생길 때 빠르게 클래스 생성 등 자동 수정 제안을 적용할 수 있다.
- Setter vs 생성자
  - 생성자 주입: 객체 생성 시점에 필수 값을 고정할 수 있어 안정적이다.
  - Setter 주입: 생성 이후 값을 바꿀 수 있어 유연하지만, 불완전 상태가 생길 수 있다.
- 빌더 패턴: 인자가 많은 생성자에서 순서 실수를 줄이고, 의미 있는 메서드 체이닝으로 가독성을 높인다.
- `toString()` 목적: 객체 상태를 사람이 읽기 쉬운 문자열로 출력해 로깅/디버깅을 쉽게 한다.
- `HttpURLConnection`: URL 연결 후 HTTP 메서드(`GET`, `POST` 등), 헤더, 요청/응답 처리를 직접 제어할 수 있다.
- Jackson 라이브러리
  - JSON 문자열을 바로 비즈니스 객체로 쓸 수 없으므로 Java 객체로 역직렬화가 필요하다.
  - 반대로 Java 객체를 JSON으로 직렬화할 때도 사용한다.

## Record 이해

- Record는 데이터를 담기 위한 간결한 불변(immutable) 데이터 캐리어다.
- 기존 DTO처럼 필드/생성자/getter/setter를 반복 작성할 필요 없이 선언을 줄여준다.
- 값은 생성 시점에 고정되며 setter가 없다.
- 체이닝 관련:
  - Record 컴포넌트 접근자는 `getXxx()`가 아니라 컴포넌트명 그대로(`rates()`)다.
  - 예: `data.rates().get("USD")`

## 상속, 추상화, 오버라이딩

- 상속은 "코드 재사용"만이 아니라 "타입 계층과 다형성"을 위한 도구다.
- `abstract`(추상화):
  - 공통 계약(메서드 이름/시그니처)을 상위에서 정의하고,
  - 하위 구현체가 실제 동작을 오버라이딩(재정의)한다.
- `WebApiExRatePaymentService`를 `PaymentService` 타입처럼 사용할 수 있는 이유는 상속/다형성 때문이다.
- 실행 시점에는 실제 객체 타입의 오버라이딩 메서드가 호출된다(동적 바인딩).

## 상속 대신 조합(Composition) + 인터페이스

- 상속 없이 `getExRate` 책임을 별도 클래스로 분리하면 결합도가 낮아진다.
- `PaymentService`는 환율 조회 구현체를 직접 갖는 대신 외부에서 주입받아 사용한다.
- 문제: 구현체마다 메서드 이름/형태가 다르면 서비스가 깨진다.
- 해결: 인터페이스로 "서비스가 기대하는 형태"를 먼저 고정한다.

### `implements` 핵심

- 구현 클래스 객체는 인터페이스 타입 변수에 담을 수 있다.
- 예:
  - `List list = new ArrayList();`
  - `ExRateProvider provider = new WebApiExRateProvider();`

## DI에서 관계 설정 책임 분리

- 인터페이스만 도입해도, 서비스를 생성하는 클라이언트가 어떤 구현체를 쓸지 여전히 직접 결정해야 한다.
- 클라이언트가 "실행 책임 + 객체 선택 책임"을 동시에 가지면 관심사가 섞인다.
- 해결:
  - `ObjectFactory` 같은 조립 전용 객체로 객체 선택/연결 책임을 분리한다.
  - 서비스는 주입받은 인터페이스로 비즈니스 로직에만 집중한다.

## 전략 패턴과 관심사의 분리

- 전략 패턴은 동작 알고리즘을 별도 전략 객체로 분리하고, 상황에 따라 교체해 쓰는 방식이다.
- 핵심은 "행위 교체 가능성"이다.

## 스프링 컨테이너와 빈(19~21강)

- 런타임에서 실제로 관리/조립되는 객체를 빈(Bean)이라 본다.
- 스프링의 `BeanFactory`/`ApplicationContext`에 의존관계 구성을 위임하면 수동 조립 부담이 줄어든다.
- `@ComponentScan`은 컴포넌트 후보를 스캔해 등록하고, `@Component`/`@Service`/`@Repository` 등은 빈 후보를 표시한다.
- 동일 타입 빈이 여러 개면 자동 주입 시 충돌이 나므로 `@Primary`, `@Qualifier`로 선택 기준을 명확히 해야 한다.
- 싱글톤 레지스트리는 객체 생명주기를 통합 관리하지만, 무분별한 전역 접근은 여전히 주의해야 한다.

## 데코레이터 패턴 + 스프링 빈 충돌 이슈(22강)

- 데코레이터 패턴: 기존 객체를 감싸 기능을 동적으로 추가한다.
- 주입 대상을 명시하지 않으면 자기 자신을 다시 주입하려다 순환 참조가 날 수 있다.
- 해결 방식:
  - 데코레이터 생성자 인자에 `@Qualifier("webApiExRateProvider")` 지정
  - 혹은 우선 빈에 `@Primary` 부여

## DIP와 분리된 인터페이스(23강)

- DIP: 상위 모듈/하위 모듈 모두 구체가 아닌 추상화에 의존해야 한다.
- `PaymentService`가 구현체가 아닌 `ExRateProvider` 인터페이스에 의존하면 DIP에 가까워진다.
- 다만 인터페이스 소유 위치가 하위 구현 패키지에 묶여 있으면 의존 방향이 깨질 수 있어,
  - 인터페이스를 상위/중립 모듈로 이동하는 Separated Interface 패턴을 적용할 수 있다.

## 오늘의 핵심 요약

1. 상속보다 조합 + 인터페이스 + DI가 변경에 강한 구조를 만든다.
2. 객체 생성/선택/연결 책임은 서비스에서 분리해 컨테이너 또는 팩토리로 위임한다.
3. 스프링은 빈 스캔/등록/주입 자동화를 제공하며, 중복 빈은 `@Primary`/`@Qualifier`로 해소한다.
4. 최종 목표는 DIP를 지키는 의존 방향(구체 -> 추상)이다.
